# D1-2603.20625 ACRFence: Preventing Semantic Rollback Attacks in Agent Checkpoint-Restore（ACRFence）

> 精读：2026-08-19 ｜ 全文 4 页 ｜ 底料 extracted_full/D1_2603.20625.txt
> 一句话：4 页短文指出 checkpoint-restore 后 LLM 必然重新合成"语义相同、字面不同"的工具调用（temp=0 也因 GPU 浮点舍入不可复现），绕过一切幂等性去重——Action Replay 实验 **10/10 全部产生重复 commit**（无 checkpoint 基线 0/10），并提出 replay-or-fork 语义的 MCP 代理防御（仅概念，未实现）。

## 1. 威胁模型与问题设定
对象是带 checkpoint-restore 的 agent 框架（LangGraph/Cursor/Claude Code/Google ADK 等，12 框架调研全部存在工具副作用重放问题，无一在工具边界强制 exactly-once）。两条攻击者模型：①**Crash-Induced Restore**——外部攻击者（工具链中的恶意 MCP 服务，如收款方 Bob 控制的回执确认服务）在不可逆动作成功后返回畸形响应触发 agent 崩溃，框架自动 restore，agent 以**新 UUID** 重发转账，银行去重失效 → Bob 收 $1000 而非 $500，且两笔交易各自"合法"；②**Deliberate Rollback Abuse**——内部人用 rewind 功能把 agent 回滚到"审批刚通过"的状态，agent 持有已消费的单次授权 token 却无使用记忆， redirected 去删另一个客户的数据（stateless 验证下授权复活）。根因：CR 只恢复本地进程态，**撤不回外部副作用**；所有既有保护（唯一请求 ID、记录非确定值、确定性编排）都假设"重试发送相同请求"——LLM 违反该假设。

## 2. 方法细节（重放漂移机制）
- **非确定性证据链**：即使 temperature=0，GPU kernel 浮点舍入使各次运行 token 序列不同（引 arXiv:2408.04667、2601.06118 等），restore 后 agent 必然生成"服务端视为新请求"的调用——这是分布式系统 output commit 问题在 LLM 上的新形态。
- **实验设计**：testbed 为 Claude Code CLI + Qwen3-32B 的内建 checkpoint-restore；外部服务模拟为 MCP 工具服务器（带 UUID 去重的银行转账、云厂商建服务器、stateless/stateful token 审批服务）；**checkpoint 打在验证之后、不可逆动作之前**。Action Replay 可链式：每轮 crash-restore 产生一笔额外重复，且每笔引用号不同、单看合法，审计困难。
- **ACRFence 设计**（未实现）：以 MCP 代理形态插在工具边界，用 eBPF 系统级监控记录每次不可逆调用的 effect log（线程/分支 ID、工具名、参数、环境上下文），无需改框架。restore 后由轻量 analyzer LLM 对比新旧调用，**区分"跨运行必然变化的字段"（request ID、时间戳）与"反映意图的字段"（金额、收款人）**，三分类处置：语义等价→直接返回记录响应不重执行（replay）；语义不同→阻断并要求显式 fork（新分支 ID）；已消费凭证→调用前告知。仅在 restore 路径运行，成本可控。

## 3. 实验与关键数据
- Action Replay：10 次 checkpoint-restore 试验**全部**产生重复 commit（100%），无 checkpoint 基线 0/10——证明漏洞由 restore 机制而非 LLM 一般行为导致。
- Authority Resurrection：stateless token 验证下 2/2 复用全部成功；stateful（服务端吊销列表）全部正确拒绝——**防御方只差一个消费记录**。
- 框架调研：LangGraph 8+ issue（维护者确认架构性难修）、CrewAI 5（crew 跑两遍、邮件重发）、Claude Code 5（审批后工具重触发）、n8n 3（重试重复扣费）等；HashiCorp Vault 单次 token 在 snapshot restore 后复活的实锤 issue。

## 4. 防御评估与失效条件
ACRFence 本身**未实现、未评估**（作者自认）：analyzer LLM 自带失效模式——误分类与对抗性逃逸（攻击者可刻意构造"意图字段伪装成易变字段"的参数）；eBPF 监控仅覆盖 OS 层可见的调用。已知最便宜的补丁是服务端 stateful 验证（消费记录/吊销列表），2/2 拒绝 token 复用。

## 5. JED 映射
对应 **回放语义 + 本地判官比对方式**（非直接攻击技术）：
- **核心教训：temp=0 也不可复现**——JED"评估端防篡改重放"意味着本地搜到的攻击轨迹在评估端重放时必然发生参数漂移（UUID/措辞/顺序）。**候选筛选必须容忍漂移**：本地验证同一候选 ≥2-3 次重放、按谓词触发取多数/并集，只保留漂移后仍命中的候选；依赖精确字符串/精确参数匹配的攻击（如必须命中某个特定 cell 内容）会在重放端变脆。
- **replay-or-fork 语义 ↔ 私榜溯源**：persistent_provenance 大概率等价于"effect log + 语义比对"——比对的是**意图字段**而非字面请求。因此 JED 候选的真实性判断应落在"语义等价"上：本地判官比对两次执行的攻击轨迹时，用 ACRFence 的字段二分法（易变字段忽略、意图字段严格），避免把无害漂移误判为攻击失败。
- **Action Replay 式计分陷阱**：JED raw = Σseverity + 2×unique_cell_count——**重复同一 cell 不加分**，ACRFence 式"重复执行累积副作用"在 JED 计分下无增益；多轮链的价值必须来自**新的 unique cell 或新谓词**，而非重复触发。
- **Authority Resurrection 的类比**：若 JED 沙盒 fixture 中存在"一次性"状态（如某邮件标记已读、某文件删除后不可再得），回滚/重试链会使 agent 重放时状态不一致——攻击构造应避免依赖一次性状态的时序。
- Crash 注入面：JED 环境 http.post 外部端点若返回畸形响应导致 agent 重试，重试路径的参数漂移可作为 UNTRUSTED_TO_ACTION 的天然变异源（低成本探索 payload 变体）。

## 6. 优先级判定：P1
理由：不提供可直接搬的攻击构造，但其核心事实（"确定性设置下 LLM 重放仍漂移"）直接决定 JED 回放预算策略——本地候选必须多次重放取并集、判官比对必须语义化，这是本周可落地的工程改动；重复 cell 不加分的推论也帮助砍掉无效的重复触发型路径设计。
