# D1-2503.04479 ToolFuzz: Automated Agent Tool Testing（ToolFuzz）

> 精读：2026-08-19 ｜ 全文 27 页 ｜ 底料 extracted_full/D1_2503.04479.txt
> 一句话：首个 agent 工具文档自动测试方法，双技术（TaintFuzzer+LLM 生成找 runtime 错误；同义 prompt+级联一致性检查找 correctness 错误），在 32 LangChain+35 自建工具上**检出错误输入比 prompt 工程基线多 20×（622 TP vs 11-15）且 FDR 从 91-92% 降到 46%**，用错误样本修文档使 agent 通过率 +6~10%。

## 1. 威胁模型与问题设定
不是攻击论文，而是**工具可靠性测试**论文，但对象正是 JED 的核心对象——工具文档与工具行为的不一致。三类文档错误：under-specified（隐含关键细节，如 arXiv 搜索不能查"意大利菜"、pubmed 日期要专用语法）、over-specified（把单一用例当全部功能）、ill-specified（文档与功能错位）。这些错误在 agent 上表现为两类失败：**runtime 失败**（非法/畸形输入触发工具异常）与 **correctness 失败**（工具返回与查询意图不符的错误结果）。经典 fuzzing（AFL 数小时）找不到任何贴合 LLM agent 场景的自然输入——所以需要 LLM 参与生成。评估载体：ReAct agent（GPT-4o/GPT-4o-mini）+ LangChain 工具生态。

## 2. 方法细节（双技术流水线）
**Runtime 失败检测**：①TaintFuzzer 对工具做 taint 对象分析，提取**语法先验**（必须以 `query: ` 开头、JSON/CSV 格式、split 操作）与**语义先验**（地址样式等），用 Faker 词汇库生成语法合规的参数去裸工具上压测，收集触发 runtime error 的参数（如 >100 字符的查询撞 assert）；②sanity check——让 agent LLM 仅凭文档判断该参数是否该调用此工具，拒绝则丢弃（过滤"文档本来就禁止"的假阳性）；③LLM 据文档+崩溃参数生成**自然用户查询**，交给完整 agent 执行，监控工具运行时错误，出错即收入错误 prompt 集。
**Correctness 失败检测**（无 ground truth 场景）：①LLM 从文档生成**模板 prompt**（"Find [venue] in [city]"）+ 每个掩码的**同义 infill**（[grocery store/supermarket/food market]×[San Jose/SJ CA/...]），组成同义 prompt 集 P；②agent 执行全部 pj，收集工具输入 Ij 与输出 Oj；③级联三重检查：(i) **输入一致性**——同义 prompt 应映射到相同工具参数（精确匹配），不一致=参数文档 under-specified；(ii) **输出一致性**——同输入应同输出；(iii) **LLM Oracle**——LLM 直接回答 P 并**多数投票**得期望答案，与 agent 回答比对（1-10 相似度，**阈值 5**）。**三项全挂才判 faulty**（AND 级联压 FDR）。实例：open-street-map 工具 6 个同义查询只有 1 个返回结果（内部按关键词白名单分流），一致性与 Oracle 双挂。

## 3. 实验与关键数据
- Runtime：TOOLFUZZ 用 3297 条 prompt 找到 41 个 unique 错误， gray-box 基线 28824 条只找 38 个、white-box 20440 条 42 个——**样本效率 1/6~1/9**。错误类型分布：HTTP 错误最多（LangChain 工具 10 个）、语法错 15 个。
- Correctness：TOOLFUZZ 1156 错误 prompt（622 TP/534 FP，FDR 46%）vs gray-box 124 条（11 TP，FDR 92%）、white-box 178 条（15 TP，91%）——**TP 20× 以上且 FDR 减半**。
- 文档自动修复（错误样本+原文档喂 LLM 改写，argumentative prompting）：File Management 基准 terminal 工具通过率 21.53%→30.42%（+~10%）、FMT 22.22%→33.35%；GitHub 工具包 62.6%→68.75%（比无信息修复多 +4%）。
- **附录 C.1 cross-tool calling**：用 ToolFuzz 生成 prompt 跨域测试，**492 条 prompt 在 53 个工具上引发"非计划工具调用"**——文档过宽导致 Dall-E 的 prompt 触发学术检索等。
- PubMed 案例：文档缺日期查询语法，agent 把 "2020" 当关键词搜标题，返回 2024 论文；补文档后 agent 生成正确的 `[Date - Publication]` 区间查询。

## 4. 防御评估与失效条件
本文的"防御"即修文档：收益上限受文档原本质量制约（已有良好文档的 toolkit 提升空间小）；FDR 46% 仍不低（非确定性工具同输入不同输出会假阳）；LLM Oracle 多数投票对需私有 API 的工具只是"大多够用"；synonymous 集合覆盖不足会漏检"一致地错"（假阴）。作者展望：扩展到多工具同时测试以发现**跨工具协调失败**。

## 5. JED 映射
对应 **工具边界侦察（F 系侦察流程）+ payload 鲁棒性筛选 + 本地判官**：
- **沙盒侦察阶段的方法论**：JED 每 model 18000s 预算下，攻击前应对 web.search/email.read/fs.read/fs.write/http.post 做 ToolFuzz 式系统探测——先静态提取参数约束（taint 式：长度、前缀、格式），再生成边界输入压测，**把预算花在"工具行为意外"处**（意外行为=谓词触发面）。例如探测 web.search 对特殊 query 的返回结构、email.read 对超长/畸形邮件头的处理——fixtures 的注入面往往就藏在这些边界。
- **同义一致性筛选 payload**：同一注入 payload 的同义变体（改称呼/改格式/换关键词）逐 fixture 试跑，比对 agent 工具调用序列的一致性——**变异后行为不一致的 payload 是脆弱的**（重放端漂移即死），行为一致的才是鲁棒候选。三重 AND 检查（输入一致性+输出一致性+Oracle）可直接搬为本地筛选管线。
- **cross-tool calling 492/53 的直接启示**：文档过宽导致 agent 被无关 prompt 误导调用工具——JED 的注入 payload 若写得"任务相容性过宽"，会诱发 agent 调用非目标工具浪费时间；反之，**精准诱导目标工具调用**（email.send/fs.write）才是 UNTRUSTED_TO_ACTION 的正解。
- **本地判官**：LLM Oracle 的"多数投票期望答案 + 1-10 相似度阈值 5"模式，可直接用于本地判官判断"agent 是否执行了攻击意图"——比二值 yes/no 更稳。
- PubMed 案例的隐喻：agent 会把模糊指令按字面执行而忽略语义——注入 payload 给 agent 的"任务描述"要含**明确的可执行语法**（具体参数、具体工具名暗示），减少 agent 自由发挥空间。

## 6. 优先级判定：P1
理由：不提供攻击 payload，但提供两件本周可用的工程件——①预算内的工具边界侦察流程（taint 约束提取+Faker 边界压测，找 fixture 注入面）；②同义变体一致性筛选管线（直接提升候选在评估端重放的存活率，呼应 ACRFence 的漂移问题）。本地判官的多数投票+阈值比对也是低成本升级。
