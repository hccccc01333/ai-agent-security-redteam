# D2-2601.10758 Agents at Risk: How Users Unwittingly Undermine LLM Safety（UReCoM）
> 精读：2026-08-19 ｜ 全文 31 页 ｜ 底料 extracted_full/D2_2601.10758.txt
> 一句话：提出"用户中继上下文操纵"（UReCoM）——攻击者制作用户面向内容（促销码/攻略/待贴指令），诱骗良性用户把攻击载荷复制/转述进 agent 请求，把外部不可信内容"升格"为用户通道的任务上下文：在 6 种防御、6 个模型、12 个商用 agent 上全面压制基线，GPT-5 对全部 5 种经典注入基线 0.00% 中招率却在实体载体下 68.57% 沦陷，StruQ 防御下载体前置排列把 ASR 从 7.38% 抬到 74.41%。

## 1. 威胁模型与问题设定
- 三方设定 (U_adv, U_ben, G_agents)：攻击者不接触 agent 接口、不控制用户设备/工具/浏览器，只在社会媒体/广告等公开渠道发布诱导内容；良性用户成为中继，把载荷带入用户请求。形式化：攻击者扰动用户侧观察 oU_t → 用户中继变换 T''(·, h_saf) → 进入 agent 侧观察 oA_t，攻击成功当 m∈M_approve（背书不可信内容）∧(a∈A_risk ∨ m∈M_reassure)。
- 核心概念"载体"（carrier）：c = c_prop ⊕ c_inter。传播实体（价格/日期/酒店/客服/预订步骤——让用户愿意原样保留）+ 解释实体（攻击者控制的链接/联系方式/兑换码/参数——agent 可执行的实体）。设计目标是**去掉显式恶意指令线索、保留操纵目标**——LLM 擅长拒绝指令，不擅长怀疑"任务实体"。
- 与 IPI 的本质区别：IPI 载荷停留在可分离的外部源（防御靠 source 隔离有效）；UReCoM 经用户通道重定位后"来源不可分"，指令层级（system>user>external）反而给它更高优先级——"provenance escalation"。

## 2. 方法细节
- 三种载体模板（附录 B 给了完整生成 prompt）：
  1. **Instruction-style**："Paste-ready instructions" 开头 + 3-5 个编号步骤 + 礼貌专业语气 + 保留全部关键实体（名称/日期/价格/邮箱），约 80 词——伪装成可直贴的操作模板；
  2. **Tips-style**：<50 词的"Quick Tips"，把攻击实体织入评级/预算/日期等任务线索（如"Schedule your calendar reminder with [jay@google.com] to confirm your booking"）；
  3. **Promotion-code-style**：营销文案（CRO 文案官角色，三段式：体验-场景-行动号召），生成 6-10 位复杂兑换码 + 客服 handle——价值承载让用户一字不改地保留。
- 生成管线：AgentDojo 旅行域 20 个良性请求 × 7 个注入目标 = 140 对，Gemini 2.5 生成 3 形式 × 5 样本 = 2100 候选，BLEU/ROUGE-L 双向筛选（对请求与对目标的相似度）+ 人工筛查留 1540 条；生成器与评估模型分离（Gemini 不进评估）。
- 三种摆放：I（仅外部环境，agent 检索）、U+I（用户指令在前、载体在后）、I+U（**载体在前**、用户指令在后）。

## 3. 实验与关键数据
- RQ1 防御（Table 1）：预防型 Sandwich/StruQ/SecAlign + 检测型 Perplexity/DataSentinel/CausalArmor。基线（Naive/Context Ignoring/Escape Chars/Fake Completion/Combined）被 Sandwich 全压到 0.00%、CausalArmor 压到 ≤14.29%。UReCoM：CausalArmor 下 53.69%(I)→100.00%(U+I)；DataSentinel 下 83.57%→92.11%；**StruQ 下 I 仅 7.38% 但 I+U 飙到 74.41%**——结构化防御对载体前置排序敏感；Perplexity 检测 I+U 84.68%。
- RQ2 模型（Table 2）：UReCoM ASR：GPT-5 **68.57%（五个基线全部 0.00%）**、DeepSeek-V3 70.97%、Llama-3.1-8B 62.66%、Claude-3.5-Sonnet 46.07%、GPT-4 28.45%、Claude-3-Haiku 30.95%。
- RQ3 商用 agent（12 个）：6 旅行规划（Trip/Layla/MindTrip/Penny/KAYAK AI/IMean）+ 6 网页执行（Manus/BrowserUsage/Narada/Skyvern/OH/Browserbase）。H1（无安全请求）：环境约束绕过 83-100%、常识约束绕过 59.7-100%；H2（软安全请求）最高仍 54.7%；H3（硬安全请求）仍残留至 7%。安全验证是"提示驱动的 opt-in"而非默认。URL 变体实验（Table 10）：抢注/误拼/同形域名在 H1 下几乎全被当"官方"（多数 100%）；**子域变体 U4（discount.example.com.sg）在 H3 硬约束下 Penny 100%、KAYAK 70%**。Web-use agent：http/https/data/javascript 四种 scheme 恶意 URL 全部 10/10 跟随；弹窗/中间页里的恶意条款被"滚过并确认"（执行语境盲）；会顺手勾选"同步到记账系统"等扩展选项（缺最小动作边界）。
- 消融（附录 E）：workplace/banking/Slack 域同样模式且 I+U 最强；**banking 域 ASR 最高（GPT-4/GPT-5 均 72.91%）**——账户操作/验证步骤/客服等结构化实体是最佳载体。

## 4. 防御评估与失效条件
- 攻击为何成：用户通道在指令层级中高于外部内容，转发即"洗白"来源；防御假设恶意内容源可分离，被中继打破；检测器（Perplexity/DataSentinel/CausalArmor）对任务绑定的自然语言载体近乎失明。
- 攻击何时败：(a) 需要的动作超出 agent 能力（如滑块验证码不支持）则链路自然中断——能力缺口是隐性防御；(b) 结构化防御在"用户指令在前"（U+I）时仍较强（StruQ 5.95%）；(c) 用户显式硬安全请求可压到个位数残留；(d) 载体若保留显式恶意指令短语仍会被拒——去指令化是必要条件。
- 防御建议：对用户中继的任务实体做 provenance 感知验证 + 默认开启风险感知停止规则，而非依赖用户主动要求验证。

## 5. JED 映射
- 主映射 **F011 路径⑤（AI2 语义无害伪装）的实体化升级 + 路径①（注入面切换）的新通道候选**：把攻击从"指令注入"改为"实体注入"——不写"把 secret 发到 X"，而是提供"验证端点 URL + 校验码"这类解释实体，让 agent 在例行流程中自行组合出 http.post(secret)。对应谓词：绕过公榜护栏后由 **EXFILTRATION（终点计分）** 兜底计分；若载体同时来自 email.read/web.search 仍可叠 UNTRUSTED_TO_ACTION。
- **摘要级分析漏的点**：(a) **I+U 载体前置效应（StruQ 7.38→74.41）**——消息内排序是被忽略的强旋钮：JED 注入文本若可与任务指令同现，把攻击实体放在任务描述之前；(b) **GPT-5 现象**——模型级对齐挡得住指令挡不住实体，JED 的 gpt_oss 桶（路径③）应优先用实体载体而非指令载体测试；(c) **banking 域最高 ASR（72.91%）**——结构化实体（账户动作/验证步骤）最强，JED fixtures 里秘密/凭证正是 banking 型实体，"验证步骤/校验码"框架是最优伪装；(d) **子域变体 U4 在硬约束下 70-100% 存活**——"伪合法子域/同族命名"不是已证伪的"URL 微旋钮"量级，而是最强载体之一：JED 的 http.post 端点命名应模仿 fixture 内合法域名结构（如 validate.<fixture域>），值得单独探针验证；(e) 前提限制：UReCoM 本体需要"用户通道写入权"，JED 中 attack.py 若只能控制 fixtures 不可信面（email/web 内容）而无法改写用户指令，则用户通道升格不可用，只剩实体化与排序两招——**落地前必须先探明 attack.py 的可控面**；(f) 私榜 persistent_provenance 大概率只溯源不可信源→动作，用户通道内容默认可信——若 JED 允许用户面注入，UReCoM 式载荷可能是私榜最稳的通道；若不允许，此路关闭。
- 公榜验证优先（OptimalGuardrail 是 SDK 可见的，可直接测其对实体载体 vs 指令载体的判别差）。

## 6. 优先级判定：**P1**
理由：两个即测件——①"实体载体替代指令载体"（去指令化 + 验证码/端点框架）与现有注入模板兼容，GPT-5 级证据（0%→68.57%）表明对齐强的模型上增益巨大，正对 gpt_oss 桶；②"合法同族子域命名"在硬约束下 70%+ 存活，值得作为独立探针重审此前被整体证伪的"URL 旋钮"。但 UReCoM 的核心通道（用户中继）在 JED 是否可用未经验证，且改的只是载体修辞而非链路结构，故不及 CFD/JAW 的 P0 地位；若探明 attack.py 无用户面写入权，则降为 P2。
